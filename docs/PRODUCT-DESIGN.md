# Alaxee Proxy — 产品设计（v4：独立工作）

> v1（读取 Clash REST API 诊断 TUN/连接）已废弃：需要 host 权限、端口维护和 mihomo 版本耦合，而且用户不想要「浏览器镜像代理客户端」。
> v2（生成 CLI 环境变量 / IDM 代理设置）已废弃：浏览器扩展无法影响浏览器之外的程序，把文档当功能卖会误导用户。
> v3（浏览器层 5 项）已落地为 v4。本文档只描述**已经实现或即将实现**的东西。

## 一句话定位

**一个只做浏览器代理这一层的 Edge 扩展**：把浏览器指向一个你自己填的 HTTP/SOCKS5 端点，并按域名决定直连还是走代理。

它不知道、也不需要知道对面是什么程序。

## 这个决定解决了什么

旧版本把 `clash` 写进数据模型：`mode: "clash"`、默认 `127.0.0.1:7890`、文案里到处是「交给 Clash」。这带来三处具体问题：

| 问题 | 现在 |
| --- | --- |
| 默认端口写死，用户装了别的代理软件或改了端口就要自己找设置 | 地址留空，首次必须填写；换软件/换端口只改一处 |
| 「跟随系统代理」模式让白名单/黑名单静默失效 | 模式删掉，只剩「走代理服务器 / 直接连接」 |
| 状态栏说「Clash 代理」，像是在和 Clash 通信 | 状态描述**浏览器当前在做什么**，端点行单独显示地址 |

架构上的收益比文案更实际：模型里不再有产品名，任何「接入 Clash 接口」的想法都必须先改数据模型，而不是靠文档禁令拦住。

## 数据模型

```
mode      : "proxy" | "direct"          默认路由
host/port : string                      用户填写，默认空
scheme    : "http" | "socks5"
localBypass: boolean                    本机地址直连，默认 true
whitelist : [{ host, includeSubdomains }]  显式直连
blacklist : [{ host, includeSubdomains }]  显式强制走代理
```

路由优先级（`resolveDomainRoute` 与生成的 PAC 完全一致）：

1. 黑名单 → 走代理
2. 本机地址（`localBypass` 开启时）→ 直连
3. 白名单 → 直连
4. 默认路由

## 已实现的设计点

### 1. 本机地址永远直连

**问题**：用 PAC 会丢掉 Chromium 内置的 bypass，本地开发服务器被送去代理，页面打不开而所有外网站点正常——几乎无法归因。

**做法**：loopback、`169.254/16`、`fe80::/10`、`.local`、无点主机名一律直连。**不含** RFC1918：公司代理常是内网唯一出口。

**开关**：默认开，可在界面关闭，关闭时先展示后果。开关计入 PAC 指纹，所以切换真正生效。

### 2. 没填地址时不假装成功

首次安装地址为空。此时：

- 可以保存规则 → 成功，但提示「浏览器代理尚未改变」；
- 切到「走代理服务器」→ 保存，但明确提示当前不生效；
- 端点行变黄，服务器卡片显示「未配置」。

不会出现「点了保存、看起来成功、实际什么都没配置」。

### 3. 规则列表可搜索、可排序、能指出是谁在生效

- 搜索按子串过滤，不改存储。
- 排序是视图操作；改写存储顺序会改变 PAC 指纹并触发无意义的下发。
- 当前网站命中的那一条带「当前网站命中」徽章——以前只显示「命中白名单」，不说哪一条。

### 4. 未知状态就说未知

浏览器代理被其他扩展/策略接管时，路由是「状态未知」，此时规则根本没生效。旧版仍会显示「命中直连白名单，浏览器会跳过代理」——自相矛盾。现在未知优先，并提示「切换上方任一模式即可重新接管」。

### 5. 状态分两层

- **胶囊**：浏览器在做什么（经代理服务器 / 直接连接 / 其他 PAC 配置 / 跟随系统代理 / 状态未知）。
- **端点行**：`浏览器代理 → socks5://127.0.0.1:7890`。

分开是因为胶囊放不下地址，而混在一起会让人以为扩展在检测对面服务。

### 6. 找端口：整个产品摩擦最大的地方

扩展故意不预填地址，代价是用户可能不知道自己代理软件的本地端口。第二版补上了三件事：

- **粘贴识别**：`127.0.0.1:7890`、`socks5://host:port`、`http://host:port`、`[::1]:7890` 都能直接认出来填进去。
- **常见端口提示**：8 个常见端口作为参考值，点一下填入，并且明确说明「只是常见默认值，请对照代理软件确认」。
- **带用户名密码的地址会被识别但提示不支持**：PAC 无法携带认证信息，静默丢弃会让用户面对一个没有解释的连接失败。

排障清单把最常见的原因放在第一条：**填了控制面板端口**（Clash 的 9090 不转发流量）。这不是猜的——它是「填了端口但不生效」的头号成因。

> 端口提示里的产品名（Clash Mixed、v2rayN、Squid）是**引用了生态常识**，不是依赖。扩展仍然不读取任何代理软件。这条界线是：可以告诉用户「7890 常见于什么」，不可以伸手去问它。

### 7. 备份与恢复

设置只存在于一个浏览器配置里，没有账号也没有云同步。导出/导入一个 JSON 文件是这条约束下唯一诚实的持久化方案。

导入**必须先预览再替换**：列出白名单/黑名单条数、模式、被丢弃的无效条目，用户确认后才写。合并两个规则列表会产生用户没审阅过的路由——域名落在错误的列表里是没有可见症状的 bug。

## 这个扩展做不到的事（不是暂缓，是做不到）

浏览器扩展只有 `proxy`、`storage`、`activeTab`（+ 可选 `tabs`）。这决定了它**只能**改 Edge 的代理设置、读标签页网址、刷新/跳转标签页。

| 需求 | 为什么做不到 | 归属 |
| --- | --- | --- |
| 判断代理程序是否在运行 | 需要 host 权限去探测本地端口 | 代理软件自身 |
| 读代理软件的节点/规则/连接 | 需要调用它的 REST API，且版本耦合 | 代理软件或其面板 |
| 让 IDM / 控制台 / Steam 走代理 | 这些进程不读浏览器的代理设置 | 系统代理或 TUN |
| TUN 开启时改变流量走向 | TUN 在网络层接管，与浏览器设置无关 | 代理软件 |
| 改 npm/pip/git 的环境变量 | 扩展不能写文件或环境变量 | 用户 shell 配置 |

TUN 开启时，扩展切换模式「没感觉」是**正常现象**，界面文案应当说明，而不是伪装成故障或功能。

## 边界：为什么"自己管订阅和节点"不在这条路上

要当代理客户端，必须能与节点服务器做 TCP/UDP 握手（Shadowsocks、VMess、Trojan、WireGuard 各有自己的协议）。浏览器扩展只有 `fetch`，它走浏览器自己的网络栈，**无法**成为原始套接字。Chrome 曾经的 `chrome.sockets` 只对 Chrome App 开放，而 Chrome App 平台已整体废弃。

所以「独立」有两层，必须分开：

| 含义 | 可行性 |
| --- | --- |
| 不依赖**特定**代理软件（换软件不用改代码） | ✅ 已实现，本就是这个产品 |
| 不需要**任何**代理软件（扩展自己连节点） | ❌ 平台不可能 |

第二层只能靠一个本地程序实现，结构是：

```
扩展 ──→ 你自己程序的本地端口 ──→ 节点
         （扩展依旧不知道对面是谁）
```

这正是当前设计的红利：因为扩展不认产品、只认地址，接一个自建后端不需要改一行扩展代码。

## 下一步优先级

1. **规则分组**（按首字母折叠），规则接近 500 条上限时才有意义。
