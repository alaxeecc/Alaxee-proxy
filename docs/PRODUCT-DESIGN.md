# Alaxee Proxy — 产品设计（v4：独立工作）

> v1（读取 Clash REST API 诊断 TUN/连接）已废弃：需要 host 权限、端口维护和 mihomo 版本耦合，而且用户不想要「浏览器镜像代理客户端」。
> v2（生成 CLI 环境变量 / IDM 代理设置）已废弃：浏览器扩展无法影响浏览器之外的程序，把文档当功能卖会误导用户。
> v3（浏览器层 5 项）已落地为 v4。本文档只描述**已经实现或即将实现**的东西。

## 一句话定位

**一个只做浏览器代理这一层的 Edge 扩展**：把浏览器指向一个你自己填的 HTTP/SOCKS5 端点，并按域名决定直连还是走代理。

它不知道、也不需要知道对面是什么程序。

## 这个决定解决了什么

旧版本把 `clash` 写进数据模型：`mode: "clash"`、默认 `127.0.0.1:7890`、文案里到处是「交给 Clash」。这带来三处具体问题：

| 问题 | 现在 |
| --- | --- |
| 默认端口写死，用户装了别的代理软件或改了端口就要自己找设置 | 地址留空，首次必须填写；换软件/换端口只改一处 |
| 「跟随系统代理」模式让白名单/黑名单静默失效 | 模式删掉，只剩「走代理服务器 / 直接连接」 |
| 状态栏说「Clash 代理」，像是在和 Clash 通信 | 状态描述**浏览器当前在做什么**，端点行单独显示地址 |

架构上的收益比文案更实际：模型里不再有产品名，任何「接入 Clash 接口」的想法都必须先改数据模型，而不是靠文档禁令拦住。

## 数据模型

```
mode      : "proxy" | "direct"          默认路由
host/port : string                      用户填写，默认空
scheme    : "http" | "socks5"
localBypass: boolean                    本机地址直连，默认 true
whitelist : [{ host, includeSubdomains }]  显式直连
blacklist : [{ host, includeSubdomains }]  显式强制走代理
```

路由优先级（`resolveDomainRoute` 与生成的 PAC 完全一致）：

1. 黑名单 → 走代理
2. 本机地址（`localBypass` 开启时）→ 直连
3. 白名单 → 直连
4. 默认路由

## 已实现的设计点

### 1. 本机地址永远直连

**问题**：用 PAC 会丢掉 Chromium 内置的 bypass，本地开发服务器被送去代理，页面打不开而所有外网站点正常——几乎无法归因。

**做法**：loopback、`169.254/16`、`fe80::/10`、`.local`、无点主机名一律直连。**不含** RFC1918：公司代理常是内网唯一出口。

**开关**：默认开，可在界面关闭，关闭时先展示后果。开关计入 PAC 指纹，所以切换真正生效。

### 2. 没填地址时不假装成功

首次安装地址为空。此时：

- 可以保存规则 → 成功，但提示「浏览器代理尚未改变」；
- 切到「走代理服务器」→ 保存，但明确提示当前不生效；
- 端点行变黄，服务器卡片显示「未配置」。

不会出现「点了保存、看起来成功、实际什么都没配置」。

### 3. 规则列表可搜索、可排序、能指出是谁在生效

- 搜索按子串过滤，不改存储。
- 排序是视图操作；改写存储顺序会改变 PAC 指纹并触发无意义的下发。
- 当前网站命中的那一条带「当前网站命中」徽章——以前只显示「命中白名单」，不说哪一条。

### 4. 未知状态就说未知

浏览器代理被其他扩展/策略接管时，路由是「状态未知」，此时规则根本没生效。旧版仍会显示「命中直连白名单，浏览器会跳过代理」——自相矛盾。现在未知优先，并提示「切换上方任一模式即可重新接管」。

### 5. 状态分两层

- **胶囊**：浏览器在做什么（经代理服务器 / 直接连接 / 其他 PAC 配置 / 跟随系统代理 / 状态未知）。
- **端点行**：`浏览器代理 → socks5://127.0.0.1:7890`。

分开是因为胶囊放不下地址，而混在一起会让人以为扩展在检测对面服务。

### 6. 找端口：整个产品摩擦最大的地方

扩展故意不预填地址，代价是用户可能不知道自己代理软件的本地端口。第二版补上了三件事：

- **粘贴识别**：`127.0.0.1:7890`、`socks5://host:port`、`http://host:port`、`[::1]:7890` 都能直接认出来填进去。
- **常见端口提示**：8 个常见端口作为参考值，点一下填入，并且明确说明「只是常见默认值，请对照代理软件确认」。
- **带用户名密码的地址会被识别但提示不支持**：PAC 无法携带认证信息，静默丢弃会让用户面对一个没有解释的连接失败。

排障清单把最常见的原因放在第一条：**填了控制面板端口**（Clash 的 9090 不转发流量）。这不是猜的——它是「填了端口但不生效」的头号成因。

> 端口提示里的产品名（Clash Mixed、v2rayN、Squid）是**引用了生态常识**，不是依赖。扩展仍然不读取任何代理软件。这条界线是：可以告诉用户「7890 常见于什么」，不可以伸手去问它。

### 7. 备份与恢复

设置只存在于一个浏览器配置里，没有账号也没有云同步。导出/导入一个 JSON 文件是这条约束下唯一诚实的持久化方案。

导入**必须先预览再替换**：列出白名单/黑名单条数、模式、被丢弃的无效条目，用户确认后才写。合并两个规则列表会产生用户没审阅过的路由——域名落在错误的列表里是没有可见症状的 bug。

### 8. 跨设备同步：用浏览器自带的，不用 Supabase

**问题**：设置只在一个浏览器配置里，换电脑要手动导出导入。

**先排除的方案**：Supabase。免费版 2 个活跃项目、闲置 1 周自动暂停。为一个 30 KB 的设置记录占一个项目名额，还要引入后端 URL、API key、服务会睡、隐私政策多一份责任——而且**同步后端睡着比没有更糟**：出差回来想恢复配置，得先去控制台唤醒它。

**采用**：`chrome.storage.sync`。它本来就免费、跟着用户的微软账号走、不需要新权限（`storage` 已覆盖），也没有需要维护的东西。

实测体积：500 条规则（上限）约 31 KB，sync 总配额 100 KB。

三个必须处理的工程问题：

1. **单项 8 KB 上限**。31 KB 放不进一个键，所以要分块（500 条 → 5 块，单项最大 7.7 KB）。
2. **写入不是原子的**。写方逐块推送，读方可能看到新 meta 配旧分块。所以每块带「代」（generation），meta 带整份负载的校验和；校验不过就整份忽略，保留本机设置。**半份规则列表和「用户删了这些规则」在界面上无法区分**，这是唯一安全的处理方式。
3. **旧代分块会泄漏**。每代都会留下分块，不清理会撞上 512 个键的上限，之后所有写入都失败。所以上传后在同一批操作里删除旧代。

**回环**：从同步区采纳设置本身也是一次写，会触发上传，把刚读到的东西推回去，而且两台设备同时做。用「上次在同步区看到的形态」比对来断开。

### 9. 规则分组：让 500 条规则能看懂

500 条规则按默认顺序排下来约 12 屏。搜索能找到某一条，但看不出列表的整体形状。

分组按可注册域名聚合：`amazon.co.uk` / `amazon.de` / `amazon.com` 各归各的组；`a.b.example.com` 和 `example.com` 落在 `example.com` 组下。

**刻意不引入公共后缀列表（PSL）**：那是为了一处纯展示用途而打包一个数据文件。改用一张常见二级后缀的小表（`co.uk`、`com.au` 等），猜错只影响标签，不影响路由。

分组顺序沿用原顺序（首次出现的组决定组位置），所以打开分组不会打乱列表。分组是**视图偏好，不持久化**——持久化会让它看起来像一次编辑，推进 `updatedAt` 并触发上传。

### 10. 合并而不是覆盖：同步的真正难点

同步最危险的不是"传不上去"，是**传上去了但对面少了一条，而且没人知道**。

两轮数据丢失都是这个形状：

| 版本 | 症状 | 根因 |
| --- | --- | --- |
| v1 | 新设备开同步，清空所有设备的规则 | 开同步被当成编辑；决策是二元的 |
| v2 | 两台设备同时编辑，其中一台的改动消失 | `local-wins` 直接上传，没有合并 |

v3 的做法是**三方合并**：负载里带 `syncBase`（双方最后同意的基准）和 `syncTombstones`（本机删除过的域名），于是任何设备都能合并，不需要自己维护历史。

规则是集合，按 host 合并天然干净。真正的冲突只有两种，都有确定答案：
- 同一 host 落在两个列表 → 按黑名单收敛（与路由一致，否则会留下一条永远不会生效的直连规则）
- 同一 host 子域标志不同 → 取较新的那条（每条规则带 `updatedAt`）

标量字段（模式、地址、端口）整组取较新的一方：它们是用户一起改的东西，交错合并会得到「A 的模式配 B 的端口」。

**一个反直觉的坑**：`syncBase` 必须是「本次合并所基于的云端记录」，不能是合并结果。设成结果等于宣称「凡是结果里有、你没有的，都是你删的」，会把对方的规则删掉。

### 11. 默认关闭，因为它暴露的是敏感信息

域名规则会暴露「哪些网站你必须绕过代理」。对一个做代理工具的用户，这可能正是最敏感的个人信息。所以：

- 默认 `syncEnabled: false`，没有任何后台写入；
- 开启前在面板里明确写出「会经过微软服务器」和它会暴露什么；
- 只同步设置和规则，不同步浏览历史、页面内容、标签页网址。

## 这个扩展做不到的事（不是暂缓，是做不到）

浏览器扩展只有 `proxy`、`storage`、`activeTab`（+ 可选 `tabs`）。这决定了它**只能**改 Edge 的代理设置、读标签页网址、刷新/跳转标签页。

| 需求 | 为什么做不到 | 归属 |
| --- | --- | --- |
| 判断代理程序是否在运行 | 需要 host 权限去探测本地端口 | 代理软件自身 |
| 读代理软件的节点/规则/连接 | 需要调用它的 REST API，且版本耦合 | 代理软件或其面板 |
| 让 IDM / 控制台 / Steam 走代理 | 这些进程不读浏览器的代理设置 | 系统代理或 TUN |
| TUN 开启时改变流量走向 | TUN 在网络层接管，与浏览器设置无关 | 代理软件 |
| 改 npm/pip/git 的环境变量 | 扩展不能写文件或环境变量 | 用户 shell 配置 |

TUN 开启时，扩展切换模式「没感觉」是**正常现象**，界面文案应当说明，而不是伪装成故障或功能。

## 边界：为什么"自己管订阅和节点"不在这条路上

要当代理客户端，必须能与节点服务器做 TCP/UDP 握手（Shadowsocks、VMess、Trojan、WireGuard 各有自己的协议）。浏览器扩展只有 `fetch`，它走浏览器自己的网络栈，**无法**成为原始套接字。Chrome 曾经的 `chrome.sockets` 只对 Chrome App 开放，而 Chrome App 平台已整体废弃。

所以「独立」有两层，必须分开：

| 含义 | 可行性 |
| --- | --- |
| 不依赖**特定**代理软件（换软件不用改代码） | ✅ 已实现，本就是这个产品 |
| 不需要**任何**代理软件（扩展自己连节点） | ❌ 平台不可能 |

第二层只能靠一个本地程序实现，结构是：

```
扩展 ──→ 你自己程序的本地端口 ──→ 节点
         （扩展依旧不知道对面是谁）
```

这正是当前设计的红利：因为扩展不认产品、只认地址，接一个自建后端不需要改一行扩展代码。

## 视觉风格：已按 alaxee-kit 落地

0.2.0 之前的视觉改动只处理**可测量的部分**：字号、对比度、溢出、错位、折叠。这些有客观标准（WCAG 数字、是否溢出、是否对齐），改了就是对的，不依赖审美判断。

品牌视觉当时刻意留白，理由是「没有 logo 就没有基准」。套件到手后这一条不再成立，本轮已按 kit 完整替换。

### 套用的是真实资产，不是近似

| 项 | 来源 | 说明 |
| --- | --- | --- |
| 身份 | 远黛 YUANDAI | 月牙 + 四角星 + 云带，玫瑰→紫红渐变，衬线字标 |
| 字形 | Noto Serif SC 子集 | 全字库 1.47 MB，UI 实际用 426 个汉字，子集 82 KB |
| 标记 | 月牙环抱四角星 | 星形用 kit 自己的三次贝塞尔路径采样，不是菱形近似 |
| 字体许可 | SIL OFL | `src/brand/fonts/OFL-NotoSerifSC.txt` 随包分发 |

### kit 的默认值没有直接用

kit 自带的 token 在原样使用时**达不到 WCAG AA**，实测：

- `accent` 在页面底色上 3.84:1，白字压在 accent 上 4.12:1，`muted` 4.25:1 — 都低于正文 4.5:1。
- 修正取值用的是 kit 自己的 hover 档（`#B5457A`），所以仍是品牌色，不是新颜色。
- `accent-soft` 从 9% 降到 5%：9% 时 accent 文字压在上面只有 4.28:1。

`tests/contrast.test.js` 守住这些比例，包括把 `rgba()` 合成到底色后再测——直接测半透明值的数字没有意义。

### 图标：状态靠颜色，不靠 kit 的时段变体

kit 提供 day / morning / noon / night 四个图标，实测平均色 `#edb0c0` / `#eaacbd` / `#f5c5cf` / `#8d6683`。前三个在 16px 下彼此无法区分，不能用来编码代理状态。

改为：**同一形状，四种颜色**。颜色之间的 OKLab ΔE 全部 ≥ 0.11（0.05 以上即「明显不同」），且每种在自身 9–11% 淡色底上仍 ≥ 4.5:1。

| 状态 | 含义 | 浅色 | 深色 |
| --- | --- | --- | --- |
| `proxy` | 交给代理 | `#B5457A` | `#EE8AB6` |
| `direct` | 浏览器直连 | `#1F6B5F` | `#5FC9B4` |
| `forced` | 命中黑名单强制走代理 | `#8F5713` | `#F0B56E` |
| `unknown` | 状态未知 | `#7C6873` | `#AD97A3` |

`forced` 不是第四种路由结果——黑名单命中在 `resolveDomainRoute` 里就是 `proxy`。它是一个**理由**图标：回答「这个页面为什么走代理」。`src/core.js` 的 `iconStateFor()` 做这个细化，路由本身不变。

### 一处实测出来的布局修正

字标最初照 kit 排成一行「远黛 YUANDAI」。380px popup 的头部只有 101px 留给文字，一行需要 128px——这正是前一轮用户讨厌的标签压缩。改成中文主字 + 下方小号字母距拉丁行：34px / 74px。`tests/layout.test.js` 现在守这条宽度预算。

### 动效

保留 kit 的呼吸与弹簧手感，但都收敛为可关：

- 四角星呼吸（3.6s），未知状态放慢到 5.4s。
- 面板入场：320ms，按 60ms 错峰淡入上浮。
- `prefers-reduced-motion` 下全部取消，不是缩短——100ms 的滑入仍然是滑入。

入场只动 `opacity` 和 `transform`：两者都在合成层，不会在 popup 还在测量自身尺寸时触发重排。这是第 10 轮「页面要短」约束的延续，`tests/layout.test.js` 会检查动画属性。

## 下一步优先级

1. **不做「连续失败兜底提示」**。它需要 `webNavigation` 权限去读全部导航事件，而收益只是"失败三次后建议切直连"。为一个提示扩大权限面、增加审核解释成本，性价比不对。这条曾经排在计划里，现在明确放弃。
2. **规则列表的批量操作**（多选删除、按组删除）。500 条规则时清空只能整组清，粒度太粗。纯前端，无新权限。
3. **导出时按分组拆分多个文件**。当前一个 JSON 装全部；规则多时便于人工审阅。

## 设计演进中的两次数据丢失

值得记录，因为它们是同一种失败：

| 版本 | 症状 | 根因 | 现在 |
| --- | --- | --- | --- |
| v1 | 新设备开同步，清空其他设备的规则 | 开同步被当成内容编辑；决策二元 | `updatedAt` 只在内容变化时推进；无编辑历史时一律读云端 |
| v2 | 两台设备同时编辑，一台的改动消失 | `local-wins` 直接上传，没有合并 | 统一为「先合并再写回」；三方合并，基准随负载传递 |

共同形状：**传上去了，但对面少了一条，而且没有任何信号**。这是同步功能唯一真正危险的失败模式，比"传不上去"危险得多。两次都是先写复现、确认、再修，修复后把复现步骤变成测试。

## 一致性的维护方式

一个不变量如果只在一个入口实现，它迟早会被绕过。已经发生过两次：

- **同一域名不能同时在两个列表**。路由层早就解决了（黑名单优先），但导入和同步合并会重新造出重复。现在 `core.reconcileRuleLists()` 是唯一实现，三条写入路径都调用它。
- **同步负载只能有一个读取者**。`sync.js` 负责分块、校验和、合并语义；控制器只调用它。`tests/package.test.js` 会检查没有别的模块直接碰 `chrome.storage.sync`。

## 验证方式

- `npm test`（182 条）：PAC 被**实际执行**，迁移、本机绕行、规则排序和未知状态提示均有覆盖。
- `node scripts/preview-server.mjs`：用 `chrome.*` 替身在普通标签页渲染真实面板，供设计评审和截图。仅开发用。
- `TESTING.md`：真机清单，包含从 0.1.x 升级的验证步骤。
